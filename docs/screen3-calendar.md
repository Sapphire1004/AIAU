# 画面 3（カレンダー）機能要件 決定記録

画面 3 の機能要件を確定させるための論点整理と、その決定内容。

決定内容は [requirements.md](requirements.md) の「画面 3: カレンダー」に反映済み。本資料は **なぜその決定になったか** を残すためのもの。認証、外部連携、通知、オフライン同期の実装契約は [バックエンド・Supabase 実装計画](backend-supabase-plan.md) を参照する。

---

## 0. この画面の役割の広さ

| 案 | 内容 | 特徴 |
| --- | --- | --- |
| A. ビューア | 表示専用。編集は画面 2 で行う | 実装が軽い。編集導線が画面 2 に一本化され迷いがない |
| B. 軽編集つきビューア | 表示に加え、時間の微調整や予定の追加・削除ができる | 当日の微修正が画面 3 で完結。画面 2 と編集機能が二重化する |
| C. カレンダーアプリ | 旅行プラン以外の予定も扱う汎用カレンダー | スコープが大きく広がる。外部カレンダー連携がほぼ必須になる |

**決定: C（汎用カレンダーアプリ）。**

画面 3 は「旅行プランの確認画面」ではなく、日常的に開くカレンダーとして作る。旅行プランはそのカレンダーに載る予定の一種という位置づけになる。

この選択により、以下が必須要件になる。

- 予定の直接編集（旅行プラン由来でない予定を扱う以上、避けられない）
- 外部カレンダーとの双方向同期（日常利用を広げる将来要件。最初の MVP には含めない）
- 通知・リマインド（日常利用するカレンダーに期待される機能）
- 既存予定との衝突検知（旅行プランを立てる際に、日常の予定と重なっていることが分かる価値が生まれる）

最後の点は案 C を選ぶ最大の利点で、画面 2 のプラン作成時に「その日は既に別の予定がある」と分かるようになる。

---

## 1. 予定の種類

最終形では出自の異なる 3 種類の予定を扱う。MVP ではプラン予定と個人予定を提供し、外部予定は将来追加する。

| 種類 | 作成元 | 画面 3 での編集 | 提供段階 |
| --- | --- | --- | --- |
| プラン予定 | 画面 2 で確定したプラン | 可（後述の同期ルールに従う） | MVP |
| 個人予定 | 画面 3 で直接作成 | 可 | MVP |
| 外部予定 | 外部カレンダーから同期 | 可（外部側へ書き戻す） | 将来拡張 |

予定の出自はカレンダー上で識別できるようにする（色分けなど）。

---

## 2. 表示単位（ビュー）

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 対応するビュー | 日 / 週 / 月 / アジェンダ（リスト）の 4 つ | 案 A では週ビューを落としたが、日常利用のカレンダーでは週ビューが主要ビューになるため必須 |
| 初期表示 | 当日。プラン画面から遷移した場合はプラン開始日 | 日常利用が主になるため、起点は当日 |

---

## 3. カレンダー上に表示する情報

**予定 1 件が持つ情報**

- タイトル、開始時刻・終了時刻（必須）
- 種類（プラン予定 / 個人予定 / 外部予定）
- プラン予定の場合は、元となった付箋・プランへの参照
- 任意: 場所、メモ、参加者、費用

**表示**

- 時間枠内: タイトル、時刻、場所名（枠の高さに収まる範囲で省略表示）
- 予定を選択したときの詳細: メモ、住所・地図リンク、費用、参加者、プラン予定なら元の付箋・チャット発言への導線
- 移動時間は「移動」という予定として明示的に置く。隙間として表現すると、移動が入らない無理なプランになっていても気づけないため。
- 終日予定（宿泊、チケットの有効期限など）は日付の上部に別枠で表示する。
- 未確定・複数案が残っている時間帯は空白にせず「未定」プレースホルダを表示する。空白だと「予定なし」と区別がつかないため。

---

## 4. 編集と、画面 2 との同期

案 C では画面 3 でも編集できるため、画面 2 と編集機能が二重化する。**どちらで編集しても同じ結果になる**ようにし、片方だけが正しい状態にならないようにする。

| 論点 | 決定 |
| --- | --- |
| 画面 3 での操作 | 予定の追加・編集・削除、ドラッグ移動、時間の伸縮 |
| プラン予定を画面 3 で編集した場合 | 画面 2 のプランに反映する（双方向同期） |
| 投票で確定した予定の変更 | 変更可能。ただし投票で確定した予定である旨を警告として表示し、変更履歴を残す |
| 変更の通知 | プランの参加者に通知する |
| 未確定・複数案が残る時間帯 | 「未定」プレースホルダを表示し、選択すると画面 2 の該当箇所へ遷移 |
| 個人予定 | 画面 2 のプランには影響しない。MVP ではプラン作成時の衝突検知にのみ使う |
| 外部予定 | 将来の外部カレンダー連携時に、衝突検知へ追加する |

---

## 5. 外部カレンダー連携

**MVPでは、確定プランの ics エクスポートのみ提供する。** Google Calendar 等からの予定取り込み、OAuth、双方向同期は実装しない。

外部カレンダー連携は将来拡張とし、実装時は provider 共通契約、同期mode、競合解決、認証・token保管を別途設計する。

---

## 6. 通知・共有・権限

- 予定開始前のリマインドをアプリ内通知と Web Push で送る。通知タイミングは予定ごとに設定でき、既定値をユーザー設定として持つ。
- プランの変更時に参加者へアプリ内通知と Web Push を送る。
- Web Push を許可しない利用者もアプリ内通知を利用できる。
- 閲覧専用リンクを発行でき、アカウントを持たない同行者も閲覧できる。共有対象はプラン予定のみとし、**個人予定・外部予定は共有しない**。
- 個人予定・外部予定は本人のみが閲覧できる。

---

## 7. 対応端末

- 計画時は PC、当日はスマホでの利用を想定し、スマホ表示に対応する。
- スマホでの主ビューはアジェンダビューと日ビュー。
- 日常利用するカレンダーとして、**オフラインでの閲覧に対応する**。オフライン時の編集はオンライン復帰後に同期する。
- オフライン中とサーバー側の両方で同じ予定が変更された場合は自動上書きせず、差分を提示してユーザーがローカル版 / サーバー版から採用する側を選択する。

---

## スコープまとめ

案 C は案 A より大きく、段階的に作る。**第 1 段階・第 2 段階はいずれも MVP の必須範囲**とし、段階は実装順を表す。

**第 1 段階（カレンダーとして成立させる）**

- 日 / 週 / 月 / アジェンダの 4 ビュー
- プラン予定の表示、「未定」プレースホルダ、移動時間・終日予定の表示
- 予定から元の付箋・チャット発言への導線、画面 2 への遷移
- 個人予定の作成・編集・削除
- スマホ対応

**第 2 段階（日常利用に耐えさせる）**

- ics エクスポート
- プラン予定の画面 3 からの編集と画面 2 への反映、変更履歴
- アプリ内通知・Web Push・リマインド
- プラン作成時の個人予定との衝突検知
- 閲覧専用リンク
- オフライン閲覧・編集同期と競合選択

**将来拡張**

- Google Calendar 等の外部カレンダー取り込み・双方向同期
- 外部予定との衝突検知
- 参加者別の別行動レーン

---

## 確定した横断方針

- MVP の外部カレンダー機能は ics エクスポートのみとし、予定取り込み・OAuth・双方向同期は将来拡張とする。
- 通知はアプリ内通知と Web Push を提供する。
- 認証は Supabase 匿名 Auth を使用し、正式アカウント化は将来拡張とする。
- データモデル、RLS、Push、共有、オフラインの実装契約は [バックエンド・Supabase 実装計画](backend-supabase-plan.md) に従う。
